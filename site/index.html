Why this exists

Agents already read Markdown tasks, design specs, handoffs, and PR notes. The missing piece is a portable way to say which context is authoritative, how much of it to retrieve, and what proof exists that the agent used the same bounded source a reviewer sees.

Value proposition

Context references become operational inputs.

01

Replace prose scavenger hunts

A task can link to a design section, fixture, or handoff with a `ctx://` URL instead of asking the agent to infer which files matter.

02

Keep context bounded

Lenses request specific projections, such as `excerpt`, so a large source file does not become an unreviewed prompt dump.

03

Make agent context auditable

Resolution can emit lens artifacts and lockfile records with registry identity, source identity, resolver identity, and content hashes.

Quickstart

Resolve a Markdown context link.

The core loop is `scan`, `validate`, then `resolve`. The resolver treats links as inert data and reads local repository paths through the registry contract.

1

Build from source

git clone https://github.com/jasonbelmonti/markdown-context.git
cd markdown-context
npm install
npm run build

Before package publication, use the source checkout and call the built CLI with `node dist/cli/index.js`.

2

Add source context and a task

mkdir -p docs
cat > docs/design.md <<'EOF'
# Resolver Design

Resolve context links only through registry-approved lenses.
EOF

cat > task.md <<'EOF'
# Implementation Task

Use [architecture context](ctx://repo/path/docs/design.md?lens=excerpt)
before changing resolver behavior.
EOF
3

Declare allowed context

cat > context.registry.json <<'EOF'
{
  "schemaVersion": "markdown-context.registry.v0",
  "registryId": "local",
  "registryVersion": "0.1.0",
  "resources": [{
    "scheme": "ctx",
    "namespace": "repo",
    "kind": "path",
    "defaultLens": "excerpt",
    "lenses": ["excerpt"],
    "params": []
  }]
}
EOF
4

Scan, validate, resolve

node dist/cli/index.js scan task.md --pretty
node dist/cli/index.js validate task.md \
  --registry context.registry.json --pretty
node dist/cli/index.js resolve task.md \
  --registry context.registry.json \
  --lockfile --pretty

Resolution

How a `ctx://` link becomes usable context.

Resolution is the point where a Markdown reference becomes an attributed packet. The CLI does not execute the URL; it validates the request, reads the approved local source, and records what was returned.

1

Extract the candidate

`scan` finds Markdown links with the `ctx://` scheme and reports the namespace, kind, identifier, requested lens, parameters, and source range.

2

Validate the contract

`validate` checks the link against the registry. Unknown kinds, unsupported lenses, and unregistered parameters fail before source content is read.

3

Render the lens

`resolve` maps `repo/path` to a repository-contained file and renders the bounded lens, such as an excerpt, with source citations.

4

Record the proof

With `--lockfile`, the output includes registry, resolver, source, artifact path, and content hash data that a reviewer can compare later.

Workflow narratives

A day in the life of an agent using it.

09:12

The task arrives with source authority attached.

The agent opens a Markdown task. Instead of scanning a whole repository for possible context, it sees a `ctx://repo/path/...` link to the relevant design note and a registry that says which lens is allowed.

09:14

Preflight separates instructions from evidence.

The agent runs `scan` and `validate`. A suspicious `prompt=` parameter would fail closed here, before it can become hidden operating guidance.

09:16

Resolution gives the agent the smallest useful packet.

The agent runs `resolve --lockfile` and receives a bounded excerpt with citations. The source text remains data; the caller's instructions still control the work.

11:03

The reviewer can inspect what informed the change.

The handoff includes the resolved artifact and lockfile record. Review can focus on source identity, registry version, resolver version, and hashes instead of guessing what the agent read.

Agent kickoff

A task starts with explicit source authority.

An engineer writes a Markdown task that links to the design spec and local fixture through `ctx://repo/path/...`. The agent scans the task, validates links against the registry, resolves bounded excerpts, and starts implementation with a compact evidence packet instead of a vague instruction to "read the docs."

CI preflight

Unsafe or unsupported context fails before review.

A pull request adds a task link with an unregistered `prompt=` parameter. Validation rejects the link before resolution runs, so prompt-like instructions cannot hide in URL parameters or become part of the agent operating context.

Review handoff

Reviewers can inspect the exact context packet.

The agent commits or attaches resolved lens artifacts and lockfile records. A reviewer checks the registry version, source identity, resolver version, artifact path, and hashes to verify what context informed the change.

Evidence model

Designed for deterministic review.

The initial surface is deliberately narrow: local Markdown, versioned registries, offline `repo/path` resolution, bounded artifacts, and stable JSON output.

Context candidate scheme, namespace, kind, id, lens, params
Registry contract allowed resources, lenses, defaults, closed params
Lens artifact bounded source data with citations
Lockfile record registry, resolver, source, artifact hash

Release fit

Small surface, high leverage.

`markdown-context` does not need MCP, a browser, live SaaS connectors, or an LLM to prove value. The first useful release gives teams a local contract for context links that agents can follow and reviewers can verify.
